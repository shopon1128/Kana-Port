汎用CLAUDE.mdの作成と運用

プロジェクトごとに書き直さず、1つの土台をコピーして削って使う

About

私が Claude Code を使って開発を進める際に読ませるCLAUDE.mdの汎用版です。 新しいプロジェクトを始めるたびにこれをコピーし、そのプロジェクトに合わせて足したり削ったりして運用しています。

あわせて、Web 固有の規約をまとめた web-dev.md と、 プロジェクトで得た学びを蓄積する LESSONS.md を併用し、 セッションを跨いでも同じ失敗を繰り返さないようにしています。 設計・デバッグなど場面ごとの手順は、Claude Code のスキルに分けて運用しています。

最終更新：2026.9.27Opus5.5用に、スキルを見直し・追加

Files

役割ごとに3つのファイルに分けています。

CLAUDE.md

どのプロジェクトでも共通の土台。基本原則・作業の進め方・事前に許可を取る操作・報告の書き方に加え、 Unity / C++ / Python / SQL / Blender の言語・ツール別セクションを持ちます。

web-dev.md

HTML / CSS / JavaScript / PHP を扱うプロジェクトだけに置く追加規約。 セキュリティ・アクセシビリティ・命名は、こちらが CLAUDE.md より優先されます。

LESSONS.md

そのプロジェクト固有の「はまった問題・意外な挙動」を1件5行前後で蓄積するファイル。 Claude には作業前に読ませ、新しい学びが出たら追記させます。

Skills

CLAUDE.md には毎回守る原則だけを書き、特定の場面でだけ必要な手順は Claude Code の「スキル」に分けています。

ほぼすべての作業で使う reality-check（記憶ではなく現物で確かめる・検証してから「完了」と言う）に加えて、次の4つを使い分けています。

design-discipline

設計の規律。作業の規模を小・中・大で判定し、中規模以上では ファイルごとの責務・主な処理の流れ・採らなかった案を示して合意を取ってから実装します。

code-design-review

実装後の設計レビュー。今後ありそうな変更を2つ具体的に想定し、触るファイルが散らばらないかで設計の良し悪しを判定します。 大きな変更は、経緯を知らないサブエージェントにレビューさせます。

visual-design

見た目の設計。コードを書く前に色・書体・レイアウトの方針を決め、 「AI が作りがちな既定の見た目」に寄っていないかを照らしてから作ります。

debug-discipline

デバッグの規律。修正より先に再現手順を確立し、仮説を1つずつ検証して、症状ではなく原因を直します。

2026年9月の見直しでは、公開されているスキル集 （obra/superpowers、anthropics/skills）を読み比べ、 そのまま導入するのではなく、自分の運用に合う考え方だけを取り込みました。

How to Use

新しいプロジェクトを始めるときの手順です。

  1. コピーする — 汎用の CLAUDE.md をプロジェクトルートにコピーします。
  2. プロジェクト情報を埋める — 概要・技術スタック・ビルド / テスト / 実行コマンド・手を触れない場所を書きます。 分からない項目は空欄で残さず行ごと消します。空欄があると、Claude が推測で補ってしまうためです。
  3. 不要なセクションを削る — 「基本原則」〜「命名規則（共通）」と「Git」はそのまま残し、 言語・ツール別のセクションは使うものだけを残します。
  4. Web を扱うなら web-dev.md も置く — 扱わない場合は、CLAUDE.md 内の web-dev.md に触れている2行を消します。
  5. LESSONS.md を育てる — 原因調査に手間取った問題や、予想と違う挙動に出会ったら、 「症状・原因・解決・教訓」の形式で追記します。誤りと分かったエントリは消します。
